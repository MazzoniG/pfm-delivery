Rules for this screen

  1. The rail gains a third item, Projects, and nothing else changes in the shell. Projects span accounts, so this page does not select one.
  2. Net cost comes from the API as the raw signed sum of the project’s lines. Spending adds to it; a refund booked to the project as income reduces it. No sign logic, the same property as net worth.
  3. Transaction count and the active date span also come from the API. Sorted by most recent activity, not by cost.
  4. Clicking a row opens the project. Rename and delete live on the project page, not in this list.

Rules for this screen

  1. Net cost is the API’s figure, the same one shown in the list.
  2. The monthly chart is the reports component reused, not copied, over the project’s lines. Months with no project spending are zero bars. Six months ending today.
  3. By category is the reports category table reused, over this project only. The share bar is presentation.
  4. Transactions list the project’s lines across every account, seen from the category side like the report: spending positive. A line that is part of a split shows its share with the entry total beneath it, both from the API, and a Split badge that opens the split editor.
  5. Show in register opens the register filtered to this project. Rename is a dialog with the name field only. Delete is on the next boards.

Rules for this screen

  1. project is a URL search param, like every other filter, so the view is shareable and back-button correct.
  2. The active filter shows as a removable chip beside the others. Removing it drops the param from the URL.
  3. Row amounts stay seen from the account, as everywhere in the register, so a split row still shows the full −230.00 that left the bank.   4. The register is account-scoped, so it shows this account’s share of the project only. When other accounts hold project transactions, one line says so, with the count from the API. The project page is the cross-account view.

Rules for this dialog

  1. The paying account line is fixed at the top and carries no project control at all. A project belongs only on income or expense lines, so the UI never offers one on an asset or liability line; the server still enforces it.
  2. The project picker lists only this user’s projects, with No project as the default. One project per line, never several: splitting the line is how an expense spans two projects.
  3. Amounts are typed as positive decimals and converted to signed minor units as strings, as in the add dialog.
  4. Lines can be added and removed. At least one line is required; one line is simply an unsplit entry.
  5. The allocated and remaining figures are the one place the browser does money arithmetic, and only in BigInt minor units through the shared money module, never a float. They are guidance: the server is authoritative, and the zero-sum trigger rejects an unbalanced entry regardless.
  6. Save stays disabled until the lines equal the total, and says why in words beside the button. Saving submits the explicit lines[] form through the existing entry endpoint.

Rules for these states

  1. The empty state explains what a project is for in one sentence and offers the same action as the header button.
  2. Deleting a project that transactions still reference is refused with a 409. The message is the detail from the problem+json body, including the count, and offers a way to those transactions. An unused project deletes normally; renaming is always allowed. There is no archive.
  3. The add dialog gains an optional Project field on Money out and Money in only. The Transfer tab has none, since both of its lines are accounts.
  4. Editing the split of a reconciled entry reuses the correction path from the register: the same editor, a callout explaining it, and the primary action reads Post correction. The original is never written to.
