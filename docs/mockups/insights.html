Rules for this screen

  1. One button, as the story asks. It generates the report for the selected period; the period lives in the URL.
  2. Grouping by meaning is a switch, off by default, and it stays off until the user turns it on and accepts the disclosure. Nothing is sent to any model before that.
  3. The largest group is marked. This is the story’s "highlight the more expensives", and it is the API’s ordering, not a client-side comparison.
  4. Groups are payees normalised by name, with the category and transaction count beneath. Amounts are the API’s strings through the formatter; the share bar is presentation, scaled to the largest row.
  5. The footnote states the matching rule in plain words, because a user who sees two spellings merged should know why.

Rules for this screen

  1. The switch writes grouping to the URL, so the view is shareable and the back button returns to the plain report.
  2. The switch label states the data boundary where the user is deciding, not only in a dialog they saw once.
  3. Groups the model produced carry a visible mark. A group of two or more payees expands to show them, each with its own figure; a group of one names its payee instead, since expanding it would repeat the same number. A grouping nobody can inspect is a grouping nobody should trust.
  4. Every amount here is a SQL sum over the model’s grouping. The model receives no amounts and returns none, so no figure on this screen originates from it.
  5. Payees the model did not group fall into Other, which always sorts last regardless of size. Nothing is dropped: the groups add up to the same total as the plain report, and if they ever do not, the report falls back to name matching rather than showing figures that do not reconcile.
  6. The note repeats what left the server, and links to the exact payload.

Name matching groups the same merchant written two ways. Grouping by meaning also puts different merchants together when they are the same kind of spending, such as a taxi company and a rideshare app.

Rules for these dialogs

  1. The disclosure names the provider. A user deciding whether data may leave should know where it goes.
  2. It states what is sent and what is not, as two lists rather than a paragraph, because the second list is the one that answers the worry.
  3. It says the feature is reversible and optional, and that the report works without it. Consent is per user and remembered; turning it off stops all sending immediately.
  4. The payload viewer shows the exact names sent and when. Nothing about this feature has to be taken on trust.

Rules for these states

  1. With no API key the switch is disabled and says why, and the report is unaffected. This is the state a fresh clone runs in.
  2. A timeout, a refused schema or an unreachable API all land here: name-matched groups, the same totals, one calm sentence. Never an error page, never a 500, never a partial report.
  3. Generating disables the button and keeps the table’s geometry. Shimmer stops under reduced motion.
  4. An empty period says so, and names the second reason a period can look empty.
